S3

Object storage

What is it?
S3 (Simple Storage Service) stores files — called objects — durably and at effectively unlimited scale, organized into containers called buckets.
Why does it exist?
Not everything belongs on a server's local disk. Static assets, backups, and uploaded files need storage that survives independently of any single instance, and scales without planning.
How this project uses it
This project's static frontend assets and backup files are stored in a private S3 bucket. The EC2 instance's IAM role is granted read/write access to that bucket only.

The Problem

Local disk storage disappears if a server is replaced, and doesn't scale past one machine. S3 solves this by decoupling storage from compute — any number of servers can read and write the same durable object store.

The Mental Model

A filing cabinet with folders
Real nested folders, files locked to one physical location.
A bucket with keys
A flat space of objects addressed by a full 'path-like' key — folders are just a naming convention, not a real hierarchy.

This project's bucket layout

cloudlab-assets/
├── images/
├── assets/
├── documents/
├── backups/

Important Concepts

Buckets
Top-level containers for objects, each with a globally unique name.
Objects
The files themselves, stored along with metadata.
Keys
An object's unique identifier inside a bucket — looks like a file path, but is really just a string.
Storage classes
Different price/retrieval-speed tiers, like Standard, Infrequent Access, and Glacier.
Bucket policies
JSON rules controlling who can access a bucket and how.
Public vs private
Whether a bucket's objects can be read by anyone on the internet, or only by authorized identities.
Static website hosting
Serving HTML/CSS/JS directly from a bucket, no server required.
Presigned URLs
A temporary, time-limited link granting access to a private object without making it public.
Versioning
Keeping every past version of an object so overwrites and deletes are recoverable.

Terminal

A realistic simulation — nothing here runs on a real server.

s3@cloudlab:~

Common Mistakes

  • Making a bucket public to 'quickly fix' an access error.
  • Forgetting that deleting an object without versioning is permanent.
  • Storing secrets or credentials as plain objects in a bucket.
  • Assuming S3 has real folders instead of key-based naming.

Mini Challenge
