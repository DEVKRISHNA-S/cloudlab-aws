IAM

Identity and access management

What is it?
IAM is AWS's front door lock and keycard system. It decides who is allowed to do what, to which resources, in your AWS account.
Why does it exist?
Without IAM, every request to AWS would either be blocked entirely or open to anyone. Applications, engineers, and automated systems all need different, narrow slices of access — never full control.
How this project uses it
This project's EC2 instance runs with an IAM role instead of stored credentials. That role only grants permission to read/write the specific S3 bucket and CloudWatch log group it needs — nothing else.

The Problem

Cloud accounts hold everything: servers, storage, databases, billing. If access were all-or-nothing, one leaked password could destroy the whole system. IAM solves this by letting you grant exactly the permissions a person or service needs, and no more.

The Mental Model

An office building
Keycards open only the doors your job requires — not the server room, not the vault.
IAM
Policies open only the AWS actions your user or service requires — not billing, not other teams' data.

How a permission is evaluated

1Identity (user or role) makes a request
2AWS checks attached IAM policies
3Policy explicitly allows the action?
4Nothing denies it?
5Request is allowed and executed
Roles over access keys
Applications should assume an IAM role rather than hardcode access keys. Roles issue short-lived, automatically-rotated credentials that never sit in your source code or a config file — so there's nothing static for an attacker to steal.

Important Concepts

Users
An identity for a person, with their own long-term credentials — used sparingly in modern setups.
Groups
A named collection of users that share the same policies, so permissions are managed once, not per-person.
Roles
A temporary identity that services (like EC2 or Lambda) can 'assume' to get short-lived permissions — no stored secrets.
Policies
A JSON document listing which actions are allowed or denied on which resources.
Least privilege
The principle of granting the smallest set of permissions needed to do a job, nothing extra.
Access keys
A long-term secret/ID pair for programmatic access — powerful, and risky if hardcoded or leaked.

Common Mistakes

  • Using the root account for everyday work instead of a scoped IAM identity.
  • Attaching the AWS-managed "AdministratorAccess" policy out of convenience.
  • Hardcoding access keys in application code or committing them to Git.
  • Writing policies with "Resource": "*" when only one bucket or table is actually needed.
