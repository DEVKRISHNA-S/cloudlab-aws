VPC

Cloud networking

What is it?
A Virtual Private Cloud is your own isolated network inside AWS — a private slice of the cloud with its own IP address range, subnets, and routing rules.
Why does it exist?
Servers need a network to talk to each other and to the internet, but not every server should be reachable from the outside world. A VPC lets you decide exactly what's public and what's private.
How this project uses it
This project runs inside a single VPC (10.0.0.0/16). The EC2 instance sits in a public subnet with a controlled path to the internet; nothing else is exposed.

The Problem

If every cloud resource were reachable from the public internet by default, any server with a bug would be an open door. A VPC solves this by making 'private by default' the starting point, then opening specific, deliberate paths in and out.

The Mental Model

A gated office campus
One address for the whole campus, separate buildings for public reception vs. internal offices, and a guarded gate controlling entry.
A VPC
One IP range for the whole network, separate subnets for public-facing vs. internal resources, and a gateway controlling internet entry.

Important Concepts

CIDR
A compact way to write an IP range, like 10.0.0.0/16 — the number after the slash says how many addresses are in the block.
Subnets
Smaller slices of the VPC's IP range, each pinned to one Availability Zone.
Public subnet
A subnet whose route table sends internet-bound traffic to an Internet Gateway.
Private subnet
A subnet with no direct route to the internet — used for databases and internal services.
Route tables
Rules that decide where network traffic from a subnet is allowed to go.
Internet Gateway
The door between the VPC and the public internet.
NAT Gateway
Lets private-subnet resources reach the internet for updates, without being reachable from it.
Security Groups
A virtual firewall attached to a resource, controlling inbound/outbound traffic by port and source.
Network ACLs
A stateless firewall attached to a subnet — a second layer of defense behind security groups.

Common Mistakes

  • Opening SSH (port 22) to 0.0.0.0/0 instead of a specific IP range.
  • Putting a database directly in a public subnet.
  • Confusing security groups (stateful, per-resource) with NACLs (stateless, per-subnet).
  • Forgetting that a public subnet only becomes public because of its route table, not its name.
