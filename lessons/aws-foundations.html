AWS Foundations

Global infrastructure & shared responsibility

What is it?
Before diving into individual services, this module covers how AWS is physically organized worldwide, how the Management Console works, and where AWS's security responsibility ends and yours begins.
Why does it exist?
Every service you'll touch — EC2, S3, VPC — lives inside this bigger picture: a specific region, a specific account, under a specific division of security responsibility.
How this project uses it
This project is deployed in a single AWS region and account, secured under the shared-responsibility model — AWS secures the physical data center and hypervisor; this project's own configuration (IAM policies, security groups, encryption) is on the project's side of the line.

The Problem

Without a shared, explicit boundary of responsibility, teams either assume AWS handles more security than it does, or duplicate effort AWS already covers. The Shared Responsibility Model draws that line explicitly.

Where AWS's responsibility ends

1AWS secures the physical data centers and hardware
2AWS secures the virtualization layer (the hypervisor)
3You secure your operating system, application, and data
4You configure IAM, security groups, and encryption correctly
5Compliance is a shared, ongoing responsibility on both sides

Important Concepts

AWS Global Infrastructure
Regions and Availability Zones distributed worldwide, so resources can run close to users and survive local failures.
Service categories
Compute, storage, database, networking, and more — the broad groupings AWS services fall into.
AWS Management Console
The web-based interface for configuring and monitoring AWS resources.
Shared Responsibility Model
AWS secures 'the cloud' (infrastructure); you secure 'what's in the cloud' (your configuration and data).
Securing accounts
Root account protection, MFA, and IAM as the first line of defense.
Securing data
Encryption at rest and in transit, and controlled access to it.
Compliance
Meeting regulatory and industry standards — a responsibility shared between AWS's certifications and your own configuration.

Common Mistakes

  • Assuming AWS's compliance certifications automatically make your application compliant.
  • Leaving the root account without MFA enabled.
  • Picking a region based on habit rather than latency, cost, or compliance needs.
  • Treating the Management Console as the only way to work with AWS, and never learning the CLI/API.
