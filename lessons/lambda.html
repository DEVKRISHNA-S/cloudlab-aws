Lambda

Serverless compute

What is it?
Lambda runs a small piece of your code in response to an event — without you provisioning or managing any server at all.
Why does it exist?
Some tasks are short, bursty, or infrequent, and don't justify a server running 24/7. Lambda lets you pay only for the milliseconds your code actually executes.
How this project uses it
A small utility function in this project — handling a specific API request — runs on Lambda instead of the always-on EC2 instance, since it only needs to run occasionally.

The Problem

Keeping a server running around the clock for a task that fires a few times a day wastes money and operational effort. Lambda solves this by executing code only when triggered, then shutting back down.

The Lambda execution flow

1An event occurs (HTTP request, file upload, schedule...)
2AWS provisions a short-lived runtime
3Your function handler runs
4A response or side effect is returned
5The environment is torn down

A Minimal Example

python 
def handler(event, context):
    return {
        "statusCode": 200,
        "body": "Hello from Lambda"
    }

When to reach for this

Prefer Lambda when
  • Work is short-lived (seconds, not hours)
  • Traffic is bursty or infrequent
  • You want zero server maintenance
Prefer EC2 when
  • The process must run continuously
  • You need full control over the OS/runtime
  • Execution time regularly exceeds Lambda's limits

Important Concepts

Functions
The unit of deployment — your code plus its runtime configuration.
Events
The trigger that invokes a function: an API call, a file upload, a schedule, etc.
Runtime
The language environment (Python, Node.js, etc.) that executes your code.
Invocation
A single execution of the function in response to one event.
Stateless execution
Nothing is guaranteed to persist between invocations — state must live elsewhere (like S3 or a database).
Cold starts
The extra latency the first time a function runs, while AWS prepares a fresh execution environment.
Permissions
Lambda functions run under an IAM role scoping exactly what they're allowed to touch.

Common Mistakes

  • Assuming local files written during execution persist to the next invocation.
  • Giving a function's role broad, unscoped permissions.
  • Ignoring cold-start latency for latency-sensitive user-facing calls.
  • Using Lambda for a workload that really needs a persistent, long-running process.

Mini Challenge

You now understand:
  • Lambda runs code only when triggered, with no server to manage
  • Execution is stateless — persistence belongs elsewhere
  • It complements EC2 rather than replacing it
